criticalIdentifiers on public project pages let any self-registered account read and overwrite other organizations' customers, invoices, projects and filesCode reading onlysrc/app/p/[slug]/page.tsx:7

How to fix

Fix all five; order by what breaks the most at once. First exposure-101 (select only name, description and document id/filename for the public page), which removes the anonymous source of ids. Then the consumers, each of which must stop trusting a client-supplied identifier: auth-104 (use the session's organization only), auth-107 (drop orgId from the tool input), auth-106 (scope the update by ctx.orgId), auth-109 (generate storage keys on the server under the organization's prefix and check the prefix on download). Treat any id that was ever on a public page as known to outsiders.

Evidence

  • File: src/app/p/[slug]/page.tsx:7 (enabler, exposure-101)
  • Code:
  const project = await db.query.projects.findFirst({
    where: (p, { and, eq }) => and(eq(p.slug, slug), eq(p.isPublic, true)),
    with: { documents: true },
  });
  if (!project) notFound();
  return <PublicProjectView project={project} />;
  • The full rows go to the client component (src/components/public-project-view.tsx:1,7), so an anonymous page response carries the project's id and orgId and each document's s3Key (src/db/schema.ts:95-96,159). /p/[slug] is outside the proxy matcher (src/proxy.ts:14-22).
  • Those identifiers are random (crypto.randomUUID() for projects, src/app/(app)/projects/actions.ts:32; Better Auth ids for organizations), so without this page an outsider has no way to obtain them. Each consumer below accepts them from any signed-in user:
  • organization id: src/app/api/export/route.ts:11 (searchParams.get("org"), auth-104) and src/server/ai/tools.ts:12,29 (model-chosen orgId, auth-107)
  • project id: src/server/trpc/routers/project.ts:24 (where(eq(projects.id, id)), returns the full row, auth-106)
  • storage key: src/app/api/uploads/route.ts:25,33 (client-chosen Key presigned and stored in the caller's own organization, then presigned for GET by src/app/api/documents/[id]/download/route.ts:26, auth-109)
  • The account those consumers need is self-service: open email sign-up (src/lib/auth.ts:12-14) and allowUserToCreateOrganization: true (src/lib/auth.ts:39).

Data flow

  • Source: anonymous GET /p/<slug> of any public project (src/app/p/[slug]/page.tsx:5-6)
  • Transformations: full project and document rows serialized into the page payload (page.tsx:7-12); the attacker's own self-registered session then carries those ids into the four consumers
  • Sink: customers query bound to the foreign organization (src/app/api/export/route.ts:23); invoices joined with customers (src/server/ai/tools.ts:29); UPDATE projects ... WHERE id = $1 RETURNING * (src/server/trpc/routers/project.ts:24); presigned PUT and later GET on the foreign object key (src/app/api/uploads/route.ts:23-27, src/app/api/documents/[id]/download/route.ts:22-30)
  • Sanitization: none on the page (no column selection) and no organization check in any of the four consumers
  • Verdict: VULNERABLE

Impact

Anyone, starting with no account and no relation to the victim, can take any organization that has a public project page and, after creating a free Ledgerly account, export that organization's whole customer list with emails, phone numbers and tax ids, pull its invoices through the assistant, edit or take down its public projects, and read or replace the files attached to them. Alone, auth-104, auth-106, auth-107 and auth-109 each need an identifier that an outsider has no way to get (only current or former members know it), and exposure-101 alone discloses one project's internal fields; together they turn every public page into an entry point for bulk cross-tenant data theft and tampering.

Rating: CRITICAL. The only credential is an account anyone can create in a minute, so in substance no authorization is needed, and the impact includes data loss (overwritten files and project fields) as well as bulk personal data of other organizations' customers. Prerequisite (1): the victim organization marked a project public, a normal product action (same as exposure-101); scale is every organization with a public page whose slug the attacker knows or guesses (slugs are short, globally unique words, src/app/(app)/projects/actions.ts:22-24, src/db/schema.ts:109).

Regression test

proof: static. Every link has its own failing test (.security-audit/tests/exposure-101.test.ts, auth-104.test.ts, auth-106.test.ts, auth-107.test.ts, auth-109.test.ts); the combined path needs a real database and an S3-compatible store end to end, which the harness does not provide. Fixing exposure-101 breaks step 1; fixing the four consumers removes the impact even if ids leak another way.
